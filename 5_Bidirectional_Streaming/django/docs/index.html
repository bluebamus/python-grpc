5_Bidirectional_Streaming — Django HTTP→gRPC 게이트웨이 Django

WSGI 의 한계와 반이중 배치(POST /chat-batch)로 양방향 RPC 를 다루는 가이드

1. 개요 — 실무에서 어디에 쓰나

Django 로 운영 중인 웹/관리자 서비스에서 양방향 스트리밍 gRPC 서비스를 호출해야 하는 경우가 있습니다. 하지만 양방향 스트리밍은 본래 지속 연결(WebSocket) 위에서 빛을 발하는데, 전통적인 Django(WSGI)는 요청-응답 단발 모델이라 진정한 양방향에 부적합합니다.

그래서 이 샘플은 현실적인 절충안으로 반이중 배치를 제공합니다. 클라이언트가 메시지 리스트를 한 번의 POST /chat-batch 로 보내면, 게이트웨이가 이를 gRPC 양방향 스트림으로 흘려보내고 서버 응답들을 모아 {"replies":[...]} 로 돌려줍니다.

요청을 모두 보낸 뒤 응답을 모으므로 반이중(half-duplex) 입니다. 양방향 RPC 자체는 그대로 쓰지만, WSGI 요청-응답 경계 안에서 한 번에 처리합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /chat-batch {"messages":["a","b","c"]} 호출
  2. Django 뷰가 JSON 파싱·검증 (문자열 리스트가 아니면 422)
  3. get_client().chat_batch(messages) 호출 — 내부에서 messages 를 ChatMessage 로 yield 하는 제너레이터를 양방향 스트림에 전달
  4. 서버가 각 메시지에 응답을 흘리고, 게이트웨이가 응답을 모두 모음
  5. 성공하면 {"replies":[...]}, 실패하면 상태코드를 HTTP 로 매핑해 응답

4. 코드 핵심 포인트

반이중 배치 (gateway/grpc_client.py)

def chat_batch(self, messages: list[str]) -> list[str]:
    def request_gen():
        for msg in messages:
            yield messages_pb2.ChatMessage(message=msg)
    responses = self._stub.Chat(request_gen())   # 양방향 RPC
    return [r.message for r in responses]

5. 실무 적용 시 고려사항

Django(WSGI)는 진정한 양방향/WebSocket 에 부적합합니다. 실시간으로 보내면서 동시에 받는 채팅·라이브 기능이 필요하면 Django Channels / ASGI 로 전환해 WebSocket consumer 안에서 gRPC 양방향 스트림을 다뤄야 합니다. 본 샘플의 /chat-batch 는 요청-응답 경계 안에서 동작하는 반이중 절충안입니다.
  • WSGI 동기 모델: 동기 뷰에서 양방향 호출은 요청 스레드를 블로킹합니다. 배치가 크거나 서버 응답이 느리면 워커 스레드가 오래 묶입니다. 배치 크기 상한과 timeout 을 함께 설계하세요.
  • 채널과 fork: gunicorn prefork 시 채널은 fork 이후(워커 안)에서 만들어야 합니다. 지연 생성(get_client)이 이를 만족합니다.
  • 메모리: 응답을 전부 모아 리스트로 반환하므로 응답이 매우 많으면 메모리를 크게 씁니다. 스트리밍 응답이 필요하면 ASGI/Channels 가 맞습니다.
  • 진짜 양방향이 필요할 때: WebSocket 게이트웨이는 같은 폴더의 FastAPI 샘플(/ws/chat)을 참고하세요.

6. 실행 · 테스트

uv sync

# 백엔드 gRPC 서버 (양방향 ChatService, 포트 50055)
uv run python manage.py runserver

# 호출
curl -X POST localhost:8000/chat-batch \
  -H "content-type: application/json" -d '{"messages":["a","b","c"]}'

# 통합 테스트
uv run pytest

통합 테스트는 echo 양방향 서버를 띄워, 보낸 메시지 개수와 동일한 개수의 replies(echo: a/b/c)를 받는지 결정론적으로 검증합니다.
