5_Bidirectional_Streaming — FastAPI HTTP→gRPC 게이트웨이 FastAPI

WebSocket 을 gRPC 양방향 스트림으로 중계하는 실시간 게이트웨이 가이드

1. 개요 — 실무에서 어디에 쓰나

채팅, 실시간 알림, 협업 편집, 라이브 시세처럼 클라이언트와 서버가 동시에 메시지를 주고받아야 하는 기능은 gRPC 양방향 스트리밍(bidirectional streaming)으로 자연스럽게 표현됩니다. 하지만 브라우저는 gRPC 스트림을 직접 말할 수 없으므로, 앞단에 WebSocket↔gRPC 게이트웨이를 두는 패턴이 흔합니다.

이 샘플의 FastAPI 게이트웨이는 WebSocket /ws/chat 으로 받은 메시지를 내부 ChatService.Chat 양방향 스트림으로 중계하고, 서버가 흘려보내는 응답을 다시 WebSocket 으로 돌려줍니다. 클라이언트는 표준 WebSocket 만 알면 됩니다.

화살표가 양방향(⇄)인 점이 핵심입니다. 요청을 다 보내기 전에도 응답이 흘러올 수 있습니다. 게이트웨이는 비동기 WebSocket 과 동기 gRPC 스트림을 큐 + 스레드로 잇습니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 ws://.../ws/chat 에 접속 → 게이트웨이가 accept
  2. 게이트웨이가 gRPC 양방향 호출을 백그라운드 스레드에서 시작 (요청 이터레이터 = 큐 구동 제너레이터)
  3. reader 코루틴: WebSocket 텍스트 수신 → send_q 에 push
  4. 제너레이터가 send_q 에서 꺼내 ChatMessage 로 yield → 서버로 전송
  5. 서버가 응답을 흘리면 스레드가 recv_q 에 넣고, writer 코루틴이 run_in_executor 로 꺼내 WebSocket 으로 send
  6. 클라이언트가 끊으면 None 센티넬로 요청 스트림을 half-close 하고 정리

4. 코드 핵심 포인트

요청 제너레이터를 큐로 구동 (main.py)

send_q = queue.Queue()

def request_gen():
    while True:
        item = send_q.get()        # WebSocket 에서 도착한 텍스트
        if item is None:           # 센티넬 → half-close
            return
        yield messages_pb2.ChatMessage(message=item)

# 블로킹 양방향 호출은 별도 스레드에서
for response in client.chat(request_gen()):
    recv_q.put(("msg", response.message))

async ⇄ sync 브리징

async def reader():   # WebSocket -> 요청큐
    text = await websocket.receive_text(); send_q.put(text)

async def writer():   # 응답큐 -> WebSocket
    item = await loop.run_in_executor(None, recv_q.get)
    await websocket.send_text(item[1])

await asyncio.gather(reader(), writer())   # 동시 구동 = 진짜 양방향

5. 실무 적용 시 고려사항

백프레셔(Backpressure)가 핵심입니다. WebSocket 입력이 gRPC 처리보다 빠르면 send_q 가 무한정 커집니다. 큐에 상한(maxsize)을 두고, 가득 차면 수신을 일시 멈추거나 연결을 종료하는 정책이 필요합니다.
  • 스레드 누수 방지: 양방향 호출은 블로킹 스레드를 점유합니다. 연결 종료 시 반드시 센티넬로 요청 스트림을 닫고 join 해야 워커가 샙니다.
  • 연결 수명/타임아웃: 유휴 연결을 무한정 열어두지 말고 keepalive/타임아웃을 둡니다. 다수의 동시 WebSocket 은 그만큼의 gRPC 스트림·스레드를 의미합니다.
  • 순서 보장: 양방향 스트림 내에서 메시지 순서는 보장되지만, 여러 연결 간 순서는 보장되지 않습니다. 애플리케이션 레벨 시퀀스가 필요할 수 있습니다.
  • 진짜 비동기 대안: 동기 스텁 + 스레드 대신 grpc.aio (asyncio 네이티브 gRPC)를 쓰면 스레드 브리징 없이 더 깔끔합니다. 본 샘플은 동기 스텁으로 큐 구동 패턴을 명확히 보이는 데 초점을 뒀습니다.
  • 인증/인가: WebSocket 핸드셰이크 시 토큰을 검증하고, 게이트웨이가 gRPC 메타데이터로 신원을 전달하는 설계를 권장합니다.

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (양방향 ChatService, 포트 50055)

uv run uvicorn app.main:app --reload

# 통합 테스트 (echo 양방향 서버를 직접 띄워 WebSocket 중계 검증)
uv run pytest

통합 테스트는 echo 서버(받은 메시지를 echo: {message} 로 반환)를 띄우고, WebSocket 으로 3개를 보내면 정확히 3개의 에코를 받는지 결정론적으로 검증합니다.
