4_Client_Streaming — Django HTTP→gRPC 게이트웨이 Django

여러 개의 입력을 gRPC 요청 스트림으로 모아 단일 응답으로 집계하는 게이트웨이 가이드

1. 개요 — 실무에서 어디에 쓰나

클라이언트 스트리밍은 클라이언트가 여러 개의 메시지를 연속으로 보내고, 서버가 그것을 모두 받은 뒤 단 하나의 응답으로 집계해 돌려주는 패턴입니다. 로그/이벤트 배치 업로드, 센서 측정값 누적, 파일 청크 업로드, 다건 트랜잭션의 일괄 집계처럼 "여러 입력 → 하나의 요약"이 필요한 곳에 적합합니다.

이 샘플은 앞단에 HTTP→gRPC 게이트웨이를 두어, 브라우저/모바일이 익숙한 REST(JSON 배열)로 한 번 호출하면 게이트웨이가 그 배열을 gRPC 요청 스트림으로 변환해 백엔드의 StreamData 를 호출하고, 집계된 단일 결과를 돌려줍니다.

2. 아키텍처 / 흐름도

브라우저 / 클라이언트

→

→

게이트웨이는 items 의 각 원소를 RequestMessage(data=...) 로 하나씩 스트리밍합니다. 서버는 스트림을 끝까지 소비한 뒤 집계 결과를 담은 ResponseMessage{result} 하나만 돌려줍니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /stream-data {"items":["a","b","c"]} 호출
  2. Django 뷰가 입력 검증 (빈 리스트/비문자열 → 422)
  3. 게이트웨이가 제너레이터로 각 item 을 RequestMessage 로 yield
  4. 재사용 중인 gRPC 스텁이 StreamData(request_iterator) 로 요청 스트림 전송
  5. 서버가 모든 요청을 받은 뒤 집계한 단일 ResponseMessage 반환
  6. 게이트웨이가 {result, count, elapsed_ms} 로 감싸 HTTP 응답

4. 코드 핵심 포인트

요청 스트림 제너레이터 (grpc_client.py)

def _request_iterator(items):
    for item in items:
        yield streaming_pb2.RequestMessage(data=item)

# 단일 응답을 받는다 (요청은 stream, 응답은 1개)
response = stub.StreamData(_request_iterator(items), timeout=timeout)
return response.result

입력 검증은 게이트웨이에서 먼저 처리합니다. items 가 비어 있으면 gRPC 를 호출하지도 않고 422 로 거절합니다.

5. 실무 적용 시 고려사항

스트림 크기와 메모리가 핵심입니다. 서버가 스트림을 전부 메모리에 모은 뒤 집계하면, 대용량 업로드에서 OOM 위험이 있습니다. 가능하면 들어오는 대로 누적(running aggregate)하거나, 게이트웨이/서버에 최대 아이템 수 제한을 두세요.
  • 백프레셔(backpressure): 클라이언트가 너무 빨리 보내면 서버가 밀립니다. gRPC 흐름 제어가 일부 흡수하지만, 게이트웨이에서 배치 크기 상한을 두는 것이 안전합니다.
  • 부분 실패의 의미: 클라이언트 스트리밍은 응답이 1개뿐이라 "몇 번째 아이템에서 실패했는지"를 표현하기 어렵습니다. 필요하면 서버 응답에 처리 개수/스킵 목록 같은 메타데이터를 포함하세요.
  • 타임아웃: timeout 은 스트림 전체에 대한 데드라인입니다. 아이템이 많을수록 넉넉히 잡아야 합니다.
  • 채널 재사용: 채널 생성은 비쌉니다. 요청마다 만들지 말고 프로세스 수명 동안 재사용하세요(본 샘플은 모듈 레벨 싱글턴).
  • 관측성: 처리한 아이템 수(count)와 소요 시간 (elapsed_ms)을 응답/로그에 남기면 성능 추세를 추적할 수 있습니다.

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제, 포트 50054)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run python manage.py runserver

# 통합 테스트 (gRPC 서버를 직접 띄워 집계/검증)
uv run pytest

통합 테스트는 "받은 요청들을 모아 개수와 연결 문자열을 result 로 반환"하는 결정론적 서버를 띄워, 게이트웨이로 ["a","b","c"] 를 보내면 count=3;data=a|b|c 가 집계되는지, 빈 리스트는 422 가 되는지를 검증합니다.
