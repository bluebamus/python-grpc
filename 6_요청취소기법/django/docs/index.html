6_요청취소기법 — Django HTTP→gRPC 게이트웨이 Django

per-call 데드라인으로 오래 걸리는 작업을 취소하고 백엔드 자원 낭비를 막는 가이드

1. 개요 — 실무에서 어디에 쓰나

리포트 생성, 대용량 변환처럼 오래 걸리는 작업은 사용자가 끝까지 기다리지 않을 수 있고, 무한정 백엔드 자원을 붙들면 안 됩니다. 게이트웨이가 호출마다 per-call 데드라인(timeout) 을 걸면, 시간 초과 시 gRPC 가 DEADLINE_EXCEEDED 를 던지고 서버 측 작업도 취소됩니다.

Django 의 기본 WSGI 는 동기 처리라 브라우저 연결 끊김을 즉시 감지하기 어렵습니다. 그래서 이 샘플은 데드라인으로 자원 사용 상한을 두는 데 집중합니다. 브라우저 이탈 감지가 꼭 필요하다면 FastAPI 샘플의 request.is_disconnected() 방식을 참고하세요.

2. 아키텍처 / 흐름도

브라우저 / 클라이언트
REST(JSON)
→
Django 게이트웨이
POST /operation
→
gRPC 채널
timeout=deadline
→
gRPC 서버
LongRunningOperation

데드라인을 넘기면 gRPC 가 DEADLINE_EXCEEDED 를 던지고, 서버 측 context.is_active() 가 False 가 되어 작업이 중단됩니다. 게이트웨이는 이를 504 로 변환해 응답합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /operation {"data":"...", "deadline_ms":500} 호출
  2. 뷰가 JSON 파싱 + 검증 (빈 문자열 → 422)
  3. 게이트웨이가 stub.LongRunningOperation(req, timeout=deadline) 로 호출
  4. 데드라인 초과 시 DEADLINE_EXCEEDED → 504 매핑. 정상 완료 시 결과 반환

4. 코드 핵심 포인트

per-call 데드라인 적용 (grpc_client.py)

request = cancel_example_pb2.Request(request_data=data)
# timeout(초) 초과 시 grpc.RpcError(DEADLINE_EXCEEDED) 발생
response = stub.LongRunningOperation(request, timeout=timeout_s)

gRPC → HTTP 매핑 (views.py)

try:
    result = get_client().long_running_operation(data, timeout=timeout_s)
except grpc.RpcError as exc:
    status = _GRPC_TO_HTTP.get(exc.code(), 500)  # DEADLINE_EXCEEDED -> 504
    return JsonResponse({"detail": exc.details()}, status=status)

취소 가능한 서버 (server 측)

def LongRunningOperation(self, request, context):
    for _ in range(STEP_COUNT):
        if not context.is_active():   # 클라이언트가 포기/취소했다
            return Response(response_data="cancelled")
        time.sleep(STEP_SECONDS)      # 오래 걸리는 작업의 한 단위
    return Response(response_data=f"completed: {request.request_data}")
gRPC StatusCodeHTTP의미
DEADLINE_EXCEEDED504데드라인 초과 → 작업 취소
CANCELLED499취소됨
UNAVAILABLE503백엔드 일시 불가
INVALID_ARGUMENT400잘못된 입력
(기타)500알 수 없는 오류

5. 실무 적용 시 고려사항

취소는 협력적(cooperative)입니다. 서버가 context.is_active() 를 주기적으로 확인하지 않으면, 데드라인이 지나도 백엔드는 작업을 끝까지 수행합니다. 오래 걸리는 루프 안에 취소 확인 지점을 두세요.
  • 데드라인 전파: 게이트웨이가 받은 데드라인을 하위 호출에도 전달해야 전체 호출 체인이 함께 끊깁니다.
  • 동기 WSGI 의 한계: 기본 Django(WSGI)는 브라우저 이탈을 즉시 감지하기 어렵습니다. ASGI + async 뷰로 가면 FastAPI 처럼 연결 끊김 감지를 구현할 수 있습니다.
  • 멱등성: 취소된 작업이 일부 부수효과를 남겼을 수 있습니다. 정리(rollback) 나 멱등 설계를 고려하세요.
  • 데드라인 값 선택: 너무 짧으면 정상 작업도 504 가 되고, 너무 길면 취소 효과가 약해집니다. SLO 기반으로 정하세요.
  • 채널 재사용: 채널 생성은 비쌉니다. 요청마다 만들지 말고 프로세스 단위로 재사용하세요(본 샘플은 get_client 로 1회 생성).

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제, 포트 50056)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run python manage.py runserver

# 통합 테스트 (gRPC 서버를 직접 띄워 데드라인/취소 검증)
uv run pytest

통합 테스트는 충분한 데드라인이면 정상 완료(200)되고, 짧은 데드라인이면 DEADLINE_EXCEEDED 가 504 로 매핑되며, 그때 서버 작업이 cancelled 로 일찍 종료되는지를 결정론적으로 검증합니다.
