6_요청취소기법 — FastAPI HTTP→gRPC 게이트웨이 FastAPI

데드라인 초과·연결 끊김을 취소로 연결해 백엔드 자원 낭비를 막는 게이트웨이 가이드

1. 개요 — 실무에서 어디에 쓰나

리포트 생성, 대용량 변환, 외부 API 집계처럼 오래 걸리는 작업은 사용자가 끝까지 기다리지 않는 경우가 많습니다. 사용자가 탭을 닫거나 요청이 너무 오래 걸리면, 백엔드가 그 작업을 계속 붙들고 있을 이유가 없습니다.

이 샘플은 HTTP→gRPC 게이트웨이가 두 가지 방식으로 작업을 취소하는 법을 보여줍니다. (1) 호출마다 per-call 데드라인(timeout) 을 걸어 시간 초과 시 DEADLINE_EXCEEDED 로 작업을 끊고, (2) 클라이언트가 연결을 끊으면 future.cancel() 로 진행 중인 gRPC 호출을 취소합니다.

데드라인을 넘기면 gRPC 가 DEADLINE_EXCEEDED 를 던지고, 서버 측 context.is_active() 가 False 로 바뀌어 작업이 중단됩니다. 게이트웨이는 이를 504 로 변환해 클라이언트에 응답합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /operation {"data":"...", "deadline_ms":500} 호출
  2. FastAPI 가 Pydantic 으로 입력 검증 (빈 문자열 → 422)
  3. 게이트웨이가 stub.LongRunningOperation.future(req, timeout=deadline) 로 비동기 호출을 시작
  4. 완료될 때까지 폴링하며, 매 틱마다 request.is_disconnected() 로 클라이언트 연결을 확인 → 끊겼으면 future.cancel()
  5. 데드라인 초과 시 future 가 DEADLINE_EXCEEDED 로 종료 → 504 매핑. 정상 완료 시 결과 반환

4. 코드 핵심 포인트

per-call 데드라인 적용 (grpc_client.py)

request = cancel_example_pb2.Request(request_data=data)
# timeout(초) = per-call 데드라인. 초과 시 future 가 DEADLINE_EXCEEDED 로 종료된다.
future = stub.LongRunningOperation.future(request, timeout=timeout_s)

연결 끊김 → 취소 (main.py)

while not future.done():
    if await request.is_disconnected():
        future.cancel()          # 백엔드 호출을 취소해 자원 낭비를 막는다
        raise HTTPException(status_code=499, detail="client disconnected")
    await asyncio.sleep(0.05)
response = future.result()       # 데드라인 초과면 여기서 RpcError 가 올라온다

취소 가능한 서버 (server 측)

def LongRunningOperation(self, request, context):
    for _ in range(STEP_COUNT):
        if not context.is_active():   # 클라이언트가 포기/취소했다
            return Response(response_data="cancelled")
        time.sleep(STEP_SECONDS)      # 오래 걸리는 작업의 한 단위
    return Response(response_data=f"completed: {request.request_data}")

5. 실무 적용 시 고려사항

취소는 협력적(cooperative)입니다. 서버가 context.is_active() 같은 신호를 주기적으로 확인하지 않으면, 클라이언트가 취소해도 백엔드는 작업을 끝까지 수행합니다. 오래 걸리는 루프 안에 취소 확인 지점을 반드시 넣으세요.
  • 데드라인 전파(deadline propagation): 게이트웨이가 받은 데드라인을 하위 호출에도 전달해야 전체 호출 체인이 함께 끊깁니다.
  • 연결 끊김 감지: FastAPI 는 request.is_disconnected() 로 브라우저 이탈을 감지할 수 있습니다. 동기 WSGI(예: 기본 Django)에서는 어렵기 때문에, per-call 데드라인으로 자원 사용 상한을 두는 것이 현실적입니다.
  • 멱등성: 취소된 작업이 이미 일부 부수효과(파일 생성, 외부 호출)를 남겼을 수 있습니다. 취소 후 정리(rollback)나 멱등 설계를 고려하세요.
  • 데드라인 값 선택: 너무 짧으면 정상 작업도 504 가 되고, 너무 길면 취소 효과가 약해집니다. 작업 특성에 맞는 SLO 기반으로 정하세요.
  • 채널 재사용: 채널 생성은 비쌉니다. 요청마다 만들지 말고 앱 수명 동안 재사용하세요(본 샘플은 lifespan 에서 1회 생성).

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제, 포트 50056)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run uvicorn app.main:app --reload

# 통합 테스트 (gRPC 서버를 직접 띄워 데드라인/취소 검증)
uv run pytest

통합 테스트는 충분한 데드라인이면 정상 완료(200)되고, 짧은 데드라인이면 DEADLINE_EXCEEDED 가 504 로 매핑되며, 그때 서버 작업이 cancelled 로 일찍 종료되는지를 결정론적으로 검증합니다.
