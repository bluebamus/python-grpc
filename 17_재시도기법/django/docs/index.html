17_재시도기법 — Django HTTP→gRPC 게이트웨이 Django

일시적 장애를 자동으로 흡수하는 게이트웨이를 실무 관점에서 구현·운영하는 가이드

1. 개요 — 실무에서 어디에 쓰나

Django 로 운영 중인 웹/관리자 서비스가 내부 gRPC 마이크로서비스를 호출하는 상황은 흔합니다. 백엔드는 배포·스케일아웃 중 잠깐 UNAVAILABLE 을 반환할 수 있는데, 이를 사용자에게 그대로 노출하면 UX 가 나빠집니다. Django 뷰가 게이트웨이 역할을 하며 gRPC 채널에 재시도 정책을 적용하면, 일시 장애를 흡수해 한 번의 매끄러운 요청으로 만들 수 있습니다.

채널/스텁은 get_client() 로 프로세스 단위 재사용됩니다. 백엔드가 일시 실패하면 채널이 자동 재시도하고, 모두 실패해야 뷰가 503 으로 변환합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /unary {"message":"Hello"} 호출
  2. Django 뷰가 JSON 파싱·검증 (빈 문자열 → 422)
  3. get_client() 로 재사용 중인 gRPC 스텁의 UnaryCall 호출
  4. 일시 실패 시 gRPC 채널이 지수 백오프로 최대 maxAttempts 회 자동 재시도
  5. 성공하면 결과를, 모두 실패하면 상태코드를 HTTP 코드로 매핑해 응답

4. 코드 핵심 포인트

설정 분리 (config/settings.py)

GRPC_TARGET = os.environ.get("GRPC_TARGET", "localhost:50051")
GRPC_RETRY_MAX_ATTEMPTS = int(os.environ.get("GRPC_RETRY_MAX_ATTEMPTS", "5"))
# ... initialBackoff / maxBackoff / multiplier

채널 재사용 (gateway/grpc_client.py)

def get_client() -> GrpcClient:
    global _client
    if _client is None:
        _client = GrpcClient()   # 채널 1회 생성 후 재사용
    return _client

5. 실무 적용 시 고려사항

멱등성(Idempotency): 재시도는 같은 요청을 여러 번 보낼 수 있으므로, 비멱등 쓰기(결제·주문)는 재시도 대상에서 제외하거나 idempotency key 로 중복을 방어해야 합니다.
  • WSGI 동기 모델: Django 동기 뷰에서 gRPC 동기 호출은 요청 스레드를 블로킹합니다. 재시도+백오프가 길어지면 워커 스레드가 묶입니다. 워커 수·타임아웃을 함께 설계하고, 대량 트래픽이면 ASGI/async 뷰나 별도 게이트웨이를 고려하세요.
  • 채널과 fork: gunicorn 등으로 prefork 할 때, 채널은 fork 이후 (워커 안)에서 만들어야 합니다. 본 샘플의 지연 생성(get_client)이 이를 만족합니다.
  • 재시도 폭주 방지: 서버 측 retryThrottling 으로 증폭을 제한하세요.
  • 타임아웃 조합: timeout 은 재시도 전체 데드라인입니다.
  • 관측성: 재시도 횟수·지연을 로깅/메트릭으로 남기세요. 본 샘플은 elapsed_ms 를 응답에 포함합니다.

6. 실행 · 테스트

uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run python manage.py runserver

# 통합 테스트
uv run pytest

통합 테스트는 "처음 N번 실패 후 성공" 서버로 재시도 동작(calls == 3)과 재시도 소진 시 503(calls == 5)을 결정론적으로 검증합니다.
