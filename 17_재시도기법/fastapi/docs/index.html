17_재시도기법 — FastAPI HTTP→gRPC 게이트웨이 FastAPI

일시적 장애를 자동으로 흡수하는 게이트웨이를 실무 관점에서 구현·운영하는 가이드

1. 개요 — 실무에서 어디에 쓰나

마이크로서비스 환경에서 백엔드 서비스는 배포·스케일아웃·일시적 네트워크 문제로 잠깐씩 UNAVAILABLE 을 반환할 수 있습니다. 클라이언트(브라우저/모바일)는 이런 일시 장애를 알 필요가 없습니다. HTTP→gRPC 게이트웨이가 앞단에서 REST 를 노출하고, 내부 gRPC 호출에 재시도 정책을 적용해 일시 장애를 흡수하면, 사용자는 한 번의 매끄러운 요청만 경험합니다.

핵심은 재시도 루프를 직접 작성하지 않는다는 점입니다. gRPC 채널의 service_config 에 정책을 선언하면 gRPC 런타임이 백오프와 함께 자동으로 재시도합니다.

응답은 역방향으로 흐릅니다. 백엔드가 UNAVAILABLE 을 던지면 gRPC 채널이 정책에 따라 자동 재시도하고, 모두 실패해야만 게이트웨이가 503 으로 변환해 클라이언트에 응답합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /unary {"message":"Hello"} 호출
  2. FastAPI 가 Pydantic 으로 입력 검증 (빈 문자열 → 422)
  3. 게이트웨이가 재사용 중인 gRPC 스텁으로 UnaryCall 호출
  4. 백엔드가 일시 실패 시, gRPC 채널이 initialBackoff→×multiplier 백오프로 최대 maxAttempts 회 자동 재시도
  5. 성공하면 결과를, 모두 실패하면 gRPC 상태코드를 HTTP 코드로 매핑해 응답

4. 코드 핵심 포인트

재시도 정책 주입 (grpc_client.py)

retry_policy = {
    "maxAttempts": 5,
    "initialBackoff": "0.1s",
    "maxBackoff": "1s",
    "backoffMultiplier": 2,
    "retryableStatusCodes": ["UNAVAILABLE"],
}
options = [
    ("grpc.enable_retries", 1),
    ("grpc.service_config",
     json.dumps({"methodConfig": [{"name": [{}], "retryPolicy": retry_policy}]})),
]
channel = grpc.insecure_channel(target, options=options)

5. 실무 적용 시 고려사항

멱등성(Idempotency)이 가장 중요합니다. 재시도는 같은 요청을 여러 번 보낼 수 있으므로, 쓰기 연산은 재시도해도 안전한 경우(멱등)에만 재시도 대상으로 삼아야 합니다. 결제·주문 생성처럼 비멱등 연산은 retryableStatusCodes 에서 빼거나 idempotency key 로 중복을 방어하세요.
  • 백오프 + 지터: 다수 클라이언트가 동시에 재시도하면 백엔드를 다시 무너뜨립니다(thundering herd). gRPC 의 지수 백오프에 더해, 백엔드 측 부하 분산을 고려하세요.
  • 재시도 폭주 방지: 재시도가 전체 트래픽을 N배로 증폭시킬 수 있습니다. 서버 측 retryThrottling (maxTokens/tokenRatio)으로 상한을 두세요.
  • 타임아웃과의 조합: timeout 은 개별 시도가 아니라 재시도 전체에 대한 데드라인입니다. 데드라인이 너무 짧으면 재시도가 무의미해집니다.
  • 재시도 가능한 코드만: UNAVAILABLE, DEADLINE_EXCEEDED 정도만 안전합니다. INVALID_ARGUMENT 같은 것은 재시도해도 항상 실패합니다.
  • 관측성: 재시도 횟수·지연을 메트릭/로그로 남겨야 "조용한 성능 저하"를 발견할 수 있습니다. 본 샘플은 elapsed_ms 를 응답에 포함합니다.
  • 채널 재사용: 채널 생성은 비쌉니다. 요청마다 만들지 말고 앱 수명 동안 재사용하세요(본 샘플은 lifespan 에서 1회 생성).

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run uvicorn app.main:app --reload

# 통합 테스트 (gRPC 서버를 직접 띄워 재시도/매핑 검증)
uv run pytest

통합 테스트는 "처음 N번 실패 후 성공"하는 서버로 재시도가 실제로 일어나는지 (calls == 3), 재시도를 모두 소진하면 503 이 되는지(calls == 5)를 결정론적으로 검증합니다.
