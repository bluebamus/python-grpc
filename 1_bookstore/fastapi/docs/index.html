1_bookstore — FastAPI protobuf 직렬화 FastAPI

gRPC 서비스 없이 protobuf 메시지를 웹 서비스의 데이터 포맷으로 쓰는 실무 가이드

1. 개요 — 왜 protobuf 직렬화인가

이 예제의 book.proto 에는 gRPC 서비스(service/rpc)가 없습니다. Book, Customer, Order(Customer customer, repeated Book items) 메시지만 정의되어 있습니다. 즉 주제는 gRPC 통신이 아니라 Protocol Buffers 를 데이터 직렬화 포맷 그 자체로 쓰는 것입니다.

protobuf 직렬화는 객체를 작고 빠른 바이너리로 바꿔, 네트워크 전송·캐시·메시지 큐· 파일 저장에 싣습니다. JSON 과 비교하면:

관점JSONprotobuf
크기필드명까지 텍스트로 반복 → 큼필드 번호+바이너리 → 작음
속도문자열 파싱바이너리 파싱 → 빠름
스키마없음(자유 형식).proto 로 강제 → 계약이 명확
가독성사람이 읽기 쉬움바이너리(사람이 못 읽음)
하위호환관례에 의존필드 번호 규칙으로 안전

실무에서는 서비스 간 메시지 포맷, Kafka 이벤트 페이로드, Redis 캐시 값, 로그/이벤트 적재 포맷 등에서 "스키마가 있고 작고 빠른" protobuf 를 데이터 포맷으로 채택합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /books {"isbn":..., "title":...} 호출
  2. FastAPI 가 Pydantic 으로 입력 검증 (필수 필드 누락 → 422)
  3. serializer.build_book() 가 JSON → book_pb2.Book 변환
  4. SerializeToString() 으로 바이너리 bytes 생성 → 길이·base64 측정
  5. ParseFromString() 으로 되돌려 원본과 == 비교 (왕복 일치 증명)
  6. 응답: {"book":{...}, "serialized_size":N, "serialized_base64":"...", "roundtrip_ok":true}

4. 코드 핵심 포인트

직렬화 / 역직렬화 왕복 (serializer.py)

book = book_pb2.Book(isbn=..., title=..., price=39.99, page_count=480)

# 직렬화: 메시지 → 바이너리 bytes
data = book.SerializeToString()

# 역직렬화: bytes → 메시지
restored = book_pb2.Book()
restored.ParseFromString(data)

# protobuf 메시지는 == 로 필드 단위 비교 → 왕복 무손실 증명
assert restored == book

중첩 + repeated (Order)

order = book_pb2.Order(
    order_number="ORD-1",
    customer=book_pb2.Customer(id="c1", name="홍길동"),   # 중첩 메시지
    items=[book_a, book_b],                               # repeated Book
)
data = order.SerializeToString()   # 중첩/리스트가 하나의 바이너리로

repeated 필드는 항목이 늘수록 직렬화 크기가 커집니다. 테스트는 items 가 2개일 때 1개보다 serialized_size 가 크다는 것으로 이를 검증합니다.

bytes 전송 (base64)

# 바이너리를 JSON/HTTP 본문에 안전하게 싣기 위해 base64 로 인코딩
serialized_base64 = base64.b64encode(data).decode("ascii")
# 받는 쪽: base64 → bytes → ParseFromString

5. 실무 적용 시 고려사항

필드 번호는 영원하다. protobuf 는 필드명이 아니라 = 1, = 2 같은 필드 번호로 바이너리를 읽습니다. 한 번 배포된 필드 번호는 재사용·변경하면 안 됩니다. 번호를 바꾸면 옛 데이터가 엉뚱한 필드로 해석됩니다.
  • 스키마 진화 / 하위호환: 새 필드는 새 번호로만 추가합니다. 구버전 리더는 모르는 필드를 무시하고(forward-compat), 신버전 리더는 빠진 필드를 기본값으로 읽습니다(backward-compat). 필드 삭제 시 번호를 reserved 로 막아 재사용을 방지합니다.
  • 필수/기본값: proto3 에는 required 가 없습니다. 빠진 필드는 기본값(빈 문자열/0)으로 채워지므로, "값이 없음"과 "기본값"을 구분해야 하면 애플리케이션 검증(이 샘플은 Pydantic) 또는 optional 키워드를 씁니다.
  • bytes 전송: 직렬화 결과는 바이너리라 JSON/텍스트 채널에 그대로 못 싣습니다. HTTP 본문에 실으려면 base64(약 33% 증가) 또는 application/octet-stream 으로 raw bytes 전송을 고려합니다.
  • JSON 대비 크기: protobuf 는 필드명을 반복하지 않아 같은 데이터를 훨씬 작게 담습니다. 트래픽/저장 비용이 큰 경로(이벤트 스트림, 캐시)에서 이점이 큽니다.
  • float 정밀도: float(32bit)는 미세 오차가 있습니다. 금액 등 정확도가 중요하면 정수(센트 단위)나 문자열/decimal 표현을 고려하세요. 본 샘플은 표시용으로 반올림합니다.
  • 스키마 공유: 송수신 양쪽이 같은 .proto 를 공유해야 합니다. proto 를 버전 관리·배포(예: buf, 사내 레지스트리)하는 체계를 갖추는 것이 실무 핵심입니다.

6. 실행 · 테스트

# proto 컴파일 (이미 생성되어 있다면 생략)
cd ../..  # python-grpc 루트
uv run python -m grpc_tools.protoc -I=1_bookstore/fastapi/app/proto \
  --python_out=1_bookstore/fastapi/app/proto \
  --grpc_python_out=1_bookstore/fastapi/app/proto book.proto

# 의존성 설치 & 앱 기동
cd 1_bookstore/fastapi
uv sync
uv run uvicorn app.main:app --reload

# 호출 예
curl -X POST localhost:8000/books -H "content-type: application/json" \
  -d '{"isbn":"978-0134685991","title":"Effective Python","price":39.99}'

# 통합 테스트 (gRPC 서버 불필요, 순수 HTTP)
uv run pytest

테스트는 (1) /health 200, (2) /books 왕복 일치(roundtrip_ok)와 크기 > 0, (3) /orders 의 repeated items 반영(크기 증가), (4) /books/decode 가 /books 의 base64 로 원본 복원, (5) 필수 필드 누락 시 422 를 검증합니다.
