14_메타데이터활용하기 — FastAPI HTTP→gRPC 게이트웨이 FastAPI

HTTP 헤더를 gRPC 메타데이터로 변환·주입하고, 응답 메타데이터를 다시 노출하는 실무 가이드

1. 개요 — 실무에서 어디에 쓰나

마이크로서비스에서 요청은 여러 서비스를 거칩니다. 이때 인증 토큰 (Authorization)과 요청 상관키(X-Request-Id)를 서비스 간에 전파해야 인증·추적·로깅이 일관되게 동작합니다. gRPC 에서는 이런 부가 정보를 메타데이터(metadata)로 전달합니다 — HTTP 헤더에 대응하는 키-값 쌍입니다.

HTTP→gRPC 게이트웨이가 앞단에서 REST 를 노출하고, 들어온 HTTP 헤더를 gRPC 메타데이터로 변환·주입하면, 백엔드 서비스는 표준 방식으로 토큰을 검증하고 요청을 추적할 수 있습니다. 게이트웨이는 또한 서버가 돌려준 메타데이터(예: 추적 ID)를 HTTP 응답으로 다시 노출합니다.

응답은 역방향으로 흐릅니다. 서버는 수신 메타데이터를 읽어 trailing metadata 로 되돌리고, 게이트웨이는 이를 HTTP 응답 바디 (request_id)와 헤더(X-Request-Id, X-Auth-Present)로 노출합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /echo {"message":"Hello"} 호출 (헤더에 Authorization, X-Request-Id 선택적 포함)
  2. FastAPI 가 Pydantic 으로 입력 검증 (빈 문자열 → 422)
  3. 게이트웨이가 X-Request-Id 가 없으면 gw-<uuid> 로 생성
  4. HTTP 헤더를 gRPC 메타데이터로 변환: authorization, x-request-id (키는 소문자)
  5. 재사용 중인 스텁으로 Echo.with_call(...) 호출, 응답과 함께 trailing_metadata() 를 회수
  6. 서버가 되돌린 메타데이터를 HTTP 응답 바디/헤더로 노출

4. 코드 핵심 포인트

HTTP 헤더 → gRPC 메타데이터 주입 (grpc_client.py)

metadata = [("x-request-id", request_id)]   # 키는 소문자여야 함
if authorization:
    metadata.append(("authorization", authorization))

response, call = stub.Echo.with_call(
    EchoRequest(message=message),
    metadata=tuple(metadata),
    timeout=5.0,
)
trailing = dict(call.trailing_metadata())   # 서버가 되돌린 메타데이터
returned_request_id = trailing.get("x-request-id", request_id)

요청 ID 생성 + 응답 헤더 노출 (main.py)

request_id = x_request_id or f"gw-{uuid.uuid4().hex}"

5. 실무 적용 시 고려사항

메타데이터 키 규약: gRPC 메타데이터 키는 반드시 소문자여야 합니다. HTTP 헤더는 대소문자를 구분하지 않지만 gRPC 는 엄격하므로, X-Request-Id → x-request-id 로 정규화해야 합니다. 또한 -bin 접미사 키는 바이너리 값으로 취급됩니다.
  • 민감 정보 전파: authorization 같은 토큰은 평문 채널에 실리지 않도록 TLS 를 사용하세요. 로그에 메타데이터를 그대로 찍으면 토큰이 유출될 수 있으니 마스킹이 필요합니다.
  • 상관관계 추적(correlation): x-request-id 를 게이트웨이에서 생성·전파하면, 여러 서비스 로그를 하나의 요청으로 묶어 추적할 수 있습니다. 이미 들어온 ID 가 있으면 보존하고, 없을 때만 생성하세요.
  • initial vs trailing: 응답을 시작하기 전에 보낼 값은 initial metadata, 응답 후에 보낼 값(상태/요약)은 trailing metadata 로 보냅니다. 본 샘플은 추적 결과를 trailing 으로 되돌립니다.
  • 화이트리스트: 모든 헤더를 무분별하게 전파하지 말고, 전파할 헤더를 명시적으로 선택하세요(토큰·추적키 등). 호스트성 헤더는 제외합니다.
  • 채널 재사용: 채널 생성은 비쌉니다. 요청마다 만들지 말고 앱 수명 동안 재사용하세요(본 샘플은 lifespan 에서 1회 생성).

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (포트 50064 로 기동)

# 게이트웨이 기동
uv run uvicorn app.main:app --reload

# 헤더로 메타데이터 전달
curl -X POST localhost:8000/echo \
  -H "content-type: application/json" \
  -H "X-Request-Id: req-123" \
  -H "Authorization: Bearer token" \
  -d '{"message":"Hello"}'

# 통합 테스트 (gRPC 서버를 직접 띄워 메타데이터 왕복 검증)
uv run pytest

통합 테스트는 클라이언트가 보낸 X-Request-Id 가 gRPC 메타데이터로 전달되고 응답 바디·헤더에 동일하게 반영되는지(request_id == sent_id), Authorization 누락/존재가 서버 메타데이터에 반영되는지를 결정론적으로 검증합니다.
