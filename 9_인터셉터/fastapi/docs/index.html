9_인터셉터 — FastAPI HTTP→gRPC 게이트웨이 FastAPI

클라이언트 인터셉터로 로깅·메타데이터 주입 같은 횡단 관심사를 한 곳에 모으는 실무 가이드

1. 개요 — 실무에서 어디에 쓰나

마이크로서비스에서 모든 gRPC 호출에 공통으로 필요한 일들이 있습니다. 요청 로깅, 분산 추적용 x-request-id 부여, 인증 토큰 첨부, 메트릭 수집 같은 횡단 관심사(cross-cutting concern)입니다. 이를 호출부마다 복붙하면 누락·불일치가 생깁니다.

클라이언트 인터셉터(grpc.UnaryUnaryClientInterceptor)는 이런 로직을 채널 한 곳에 모읍니다. 인터셉터를 채널에 씌우면 그 채널의 모든 unary 호출이 자동으로 가로채져, 비즈니스 코드에는 보일러플레이트가 남지 않습니다. 본 샘플은 게이트웨이가 백엔드를 호출할 때 인터셉터로 (1) 호출을 로깅하고 (2) x-request-id 를 자동 주입합니다.

호출은 항상 인터셉터를 거칩니다. 인터셉터가 메타데이터에 x-request-id 가 없으면 새로 만들어 주입하고, 서버는 그 값을 받아 처리합니다. 본 샘플의 서버는 받은 값을 trailing metadata 로 되돌려주어 게이트웨이가 응답에 함께 실어 반환합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /echo {"message":"Hello"} 호출
  2. FastAPI 가 Pydantic 으로 입력 검증 (빈 문자열 → 422)
  3. 게이트웨이가 재사용 중인 gRPC 스텁으로 Echo 호출
  4. 인터셉터가 가로채 호출을 로깅하고, x-request-id 가 없으면 uuid4 로 생성해 메타데이터에 주입(+호출 카운트 증가)
  5. 서버가 메시지를 echo 하고 x-request-id 를 응답에 반영
  6. 게이트웨이가 {message, request_id, elapsed_ms} 로 응답. 실패 시 gRPC 상태코드를 HTTP 코드로 매핑

4. 코드 핵심 포인트

클라이언트 인터셉터 (grpc_client.py)

class LoggingRequestIdInterceptor(grpc.UnaryUnaryClientInterceptor):
    def intercept_unary_unary(self, continuation, details, request):
        metadata = list(details.metadata or [])
        if not any(k.lower() == "x-request-id" for k, _ in metadata):
            metadata.append(("x-request-id", uuid.uuid4().hex))   # 자동 주입
        new_details = _replace_metadata(details, metadata)
        self._call_count += 1                                       # 실행 증거
        logger.info("gRPC 호출 시작 ...")
        response = continuation(new_details, request)               # 실제 호출
        logger.info("gRPC 호출 종료 ...")
        return response

채널에 인터셉터 적용

base = grpc.insecure_channel(target)
channel = grpc.intercept_channel(base, LoggingRequestIdInterceptor())
stub = EchoServiceStub(channel)   # 이후 모든 호출이 인터셉터를 거친다

grpc.ClientCallDetails 는 불변이므로, 메타데이터를 추가하려면 같은 필드를 가진 새 객체로 교체해야 합니다(본 샘플은 namedtuple 사용).

5. 실무 적용 시 고려사항

인터셉터 체인 순서가 중요합니다. 여러 인터셉터를 적용하면 등록 순서대로 감싸집니다. 인증→로깅→재시도처럼 의존 관계가 있는 로직은 순서를 신중히 정하세요.
  • 불변 ClientCallDetails: 메타데이터를 바꾸려면 새 객체로 교체해야 합니다. 기존 메타데이터를 보존한 채 추가만 하세요(덮어쓰기 주의).
  • 스트리밍은 별도 인터페이스: unary-unary 외에 unary-stream, stream-unary, stream-stream 용 인터셉터가 따로 있습니다. 필요한 호출 형태마다 구현하세요.
  • 예외/상태 처리: continuation() 이 던지는 RpcError 를 인터셉터에서 잡아 로깅/메트릭에 반영할 수 있습니다. 단, 의미를 바꾸지 않도록 다시 던지세요.
  • 분산 추적: x-request-id(또는 W3C traceparent)를 모든 hop 에 전파하면 로그를 하나의 추적 ID 로 묶을 수 있습니다.
  • 관측성: 인터셉터는 호출 수·지연·에러율을 수집하기 가장 좋은 지점입니다. 본 샘플은 call_count 와 elapsed_ms 를 노출합니다.
  • 채널 재사용: 채널 생성은 비쌉니다. 인터셉터를 씌운 채널을 앱 수명 동안 재사용하세요(본 샘플은 lifespan 에서 1회 생성).

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제, 포트 50059)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run uvicorn app.main:app --reload

# 통합 테스트 (gRPC 서버를 직접 띄워 인터셉터 동작 검증)
uv run pytest

통합 테스트는 인터셉터가 주입한 x-request-id 가 서버까지 전달되어 응답에 되돌아오는지, 그리고 호출마다 call_count 가 증가하는지를 결정론적으로 검증합니다(인터셉터가 실제로 실행되었다는 단언).
