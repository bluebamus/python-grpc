3_ServerStreaming — FastAPI HTTP→gRPC 게이트웨이 FastAPI

gRPC 서버 스트리밍(요청 1 → 응답 다수)을 HTTP 스트리밍(SSE)으로 중계하는 실무 가이드

1. 개요 — 실무에서 어디에 쓰나

LLM 토큰 스트리밍, 실시간 알림/피드, 진행률(progress) 전송, 로그 tailing 처럼 하나의 요청에 대해 결과가 여러 조각으로 시간차를 두고 도착하는 상황이 많습니다. 백엔드를 gRPC 서버 스트리밍으로 구현하면 이런 흐름을 자연스럽게 표현할 수 있지만, 브라우저는 gRPC 스트림을 직접 받기 어렵습니다.

그래서 HTTP→gRPC 게이트웨이가 앞단에서 REST 를 노출하고, 내부 gRPC 서버 스트림을 받아 SSE(text/event-stream) 로 변환해 흘려보냅니다. 핵심은 응답을 모아서 한 번에 주지 않는다는 점입니다. 서버가 보내는 메시지를 받는 즉시 클라이언트로 중계해, 첫 바이트까지의 지연(TTFB)을 줄입니다.

요청은 1개({"message":"..."})지만, 응답은 서버가 yield 하는 만큼 여러 개가 stream 으로 돌아옵니다. 게이트웨이의 제너레이터가 이 스트림을 순회하며 메시지마다 data: {json}\n\n SSE 이벤트를 yield 합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /chat-stream {"message":"시작"} 호출
  2. FastAPI 가 Pydantic 으로 입력 검증 (빈 문자열 → 422)
  3. 게이트웨이가 재사용 중인 스텁으로 ChatStream 호출 → 응답 iterator 획득
  4. 첫 메시지를 미리 한 번 당겨(peek) 본다 — 여기서 백엔드가 UNAVAILABLE 이면 스트림 시작 전이라 503 으로 매핑 가능
  5. 이후 StreamingResponse 가 제너레이터를 돌며 도착하는 메시지마다 SSE 이벤트를 흘려보내고, 끝나면 event: done 으로 마무리

4. 코드 핵심 포인트

서버 스트림 순회 (grpc_client.py)

def chat_stream(self, message, timeout=None):
    request = message_pb2.ChatMessage(message=message)
    call = self._stub.ChatStream(request, timeout=timeout)
    for response in call:        # 응답이 도착하는 대로 하나씩
        yield response.message   # 제너레이터로 흘려보냄

SSE 로 중계 (main.py)

def event_generator():
    for message in stream:
        yield f"data: {json.dumps({'message': message})}\n\n"
    yield "event: done\ndata: {...}\n\n"

return StreamingResponse(event_generator(), media_type="text/event-stream")

5. 실무 적용 시 고려사항

스트림 시작 후에는 HTTP 상태코드를 바꿀 수 없습니다. 첫 바이트를 보내는 순간 상태줄(200)이 확정되므로, 도중 실패는 본문 안의 error 이벤트로 알려야 합니다. 본 샘플은 첫 메시지를 미리 당겨(peek) 초기 실패만 503 등으로 매핑합니다.
  • 버퍼링 주의: 중간 프록시(Nginx 등)나 응답 버퍼가 SSE 를 모아버리면 스트리밍 효과가 사라집니다. X-Accel-Buffering: no, 압축 비활성 등을 고려하세요.
  • 연결 종료/취소 전파: 클라이언트가 끊으면 gRPC 호출도 call.cancel() 로 취소해 백엔드 자원을 낭비하지 않도록 해야 합니다.
  • 동기 vs 비동기: 본 샘플은 동기 스텁을 사용합니다. 동시 스트림이 많으면 워커 스레드가 묶일 수 있으니, 대량 트래픽에서는 grpc.aio + async 제너레이터를 고려하세요.
  • 하트비트: 메시지 간 간격이 길면 중간 장비가 유휴 연결을 끊을 수 있습니다. 주기적인 코멘트(: ping\n\n) 이벤트로 연결을 유지하세요.
  • 채널 재사용: 채널 생성은 비쌉니다. 요청마다 만들지 말고 앱 수명 동안 재사용하세요(본 샘플은 lifespan 에서 1회 생성).

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제, 포트 50053)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run uvicorn app.main:app --reload

# SSE 스트림 수신 (-N 으로 버퍼 끄기)
curl -N -X POST localhost:8000/chat-stream \
  -H "content-type: application/json" -d '{"message":"시작"}'

# 통합 테스트 (gRPC 서버를 직접 띄워 N개 수신 검증)
uv run pytest

통합 테스트는 서버가 정확히 N개(예: 3개)를 stream 으로 보낼 때 게이트웨이를 통해 클라이언트가 N개를 순서대로 모두 수신하는지(messages == [..#0, ..#1, ..#2]), 백엔드 부재 시 503 으로 매핑되는지를 결정론적으로 검증합니다.
