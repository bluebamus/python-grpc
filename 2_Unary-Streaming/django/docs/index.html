2_Unary-Streaming — Django HTTP→gRPC 게이트웨이 Django

가장 기본적인 Unary RPC(SayHello)를 REST 로 감싸는 게이트웨이 실무 가이드

1. 개요 — 실무에서 어디에 쓰나

Django 로 운영 중인 웹/관리자 서비스가 내부 gRPC 마이크로서비스를 호출하는 상황은 흔합니다. 브라우저는 REST(JSON)를 기대하지만 내부는 gRPC 로 통신하므로, Django 뷰가 게이트웨이 역할을 하며 REST 요청을 gRPC 호출로 변환합니다. 이 예제는 가장 단순한 Unary RPC(요청 1 : 응답 1)인 Greeter.SayHello 를 감싸는 패턴을 보여줍니다.

2. 아키텍처 / 흐름도

채널/스텁은 get_client() 로 프로세스 단위 재사용됩니다. 백엔드가 에러를 던지면 뷰가 gRPC 상태코드를 HTTP 코드로 변환합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /hello {"name":"World"} 호출
  2. Django 뷰가 JSON 파싱·검증 (빈 문자열 → 422)
  3. get_client() 로 재사용 중인 gRPC 스텁의 SayHello(HelloRequest(name)) 호출
  4. 백엔드가 HelloReply(message) 반환
  5. 뷰가 {"message": ..., "elapsed_ms": ...} 로 응답

4. 코드 핵심 포인트

설정 분리 (config/settings.py)

GRPC_TARGET = os.environ.get("GRPC_TARGET", "localhost:50052")

채널 재사용 (gateway/grpc_client.py)

def get_client() -> GrpcClient:
    global _client
    if _client is None:
        _client = GrpcClient()   # 채널 1회 생성 후 재사용
    return _client

5. 실무 적용 시 고려사항

이중 검증: 게이트웨이는 JSON 파싱·검증을 하지만, 백엔드 역시 자체 검증을 합니다. 게이트웨이를 우회하는 다른 클라이언트가 있을 수 있으므로 백엔드 검증이 신뢰의 최종 경계입니다. 본 샘플은 백엔드의 INVALID_ARGUMENT 도 400 으로 매핑해 일관된 의미를 유지합니다.
  • WSGI 동기 모델: Django 동기 뷰에서 gRPC 동기 호출은 요청 스레드를 블로킹합니다. 모든 호출에 timeout 을 두어 워커가 무한정 묶이지 않게 하세요(본 샘플 timeout=5.0).
  • 채널과 fork: gunicorn 등으로 prefork 할 때, 채널은 fork 이후 (워커 안)에서 만들어야 합니다. 본 샘플의 지연 생성(get_client)이 이를 만족합니다.
  • 스키마 분리: proto 메시지를 그대로 노출하지 말고 REST 응답 형태를 따로 두세요. 내부 proto 변경이 외부 API 계약으로 새지 않습니다.
  • 에러 매핑 일관성: gRPC 상태코드↔HTTP 코드 매핑 표를 한 곳에 모아 모든 엔드포인트가 같은 규칙을 쓰게 하세요.
  • 관측성: 응답 지연을 로깅/메트릭으로 남기세요. 본 샘플은 elapsed_ms 를 응답에 포함합니다.

6. 실행 · 테스트

uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제, 포트 50052)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run python manage.py runserver

# 통합 테스트
uv run pytest

통합 테스트는 결정론적 Greeter 서버로 /health 200, 정상 SayHello 성공(Hello, World!), 빈 name → 422, 백엔드 INVALID_ARGUMENT → 400 을 검증합니다.
