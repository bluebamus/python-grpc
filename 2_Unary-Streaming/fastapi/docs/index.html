2_Unary-Streaming — FastAPI HTTP→gRPC 게이트웨이 FastAPI

가장 기본적인 Unary RPC(SayHello)를 REST 로 감싸는 게이트웨이 실무 가이드

1. 개요 — 실무에서 어디에 쓰나

내부 마이크로서비스는 흔히 gRPC 로 통신하지만, 브라우저·모바일·외부 파트너는 여전히 REST(JSON)를 기대합니다. HTTP→gRPC 게이트웨이는 앞단에서 REST 를 노출하고, 요청을 내부 gRPC 호출로 변환합니다. 이 예제는 그 중 가장 단순한 형태인 Unary RPC(요청 1 : 응답 1)를 감싸는 패턴을 보여줍니다.

핵심은 경계 분리입니다. 외부 계약(REST/Pydantic 스키마)과 내부 계약(proto 메시지)을 분리해, 한쪽 변경이 다른 쪽으로 곧바로 새지 않게 합니다.

응답은 역방향으로 흐릅니다. 백엔드가 에러를 던지면 게이트웨이가 gRPC 상태코드를 HTTP 코드로 변환해 클라이언트에 응답합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /hello {"name":"World"} 호출
  2. FastAPI 가 Pydantic 으로 입력 검증 (빈 문자열 → 422)
  3. 게이트웨이가 재사용 중인 gRPC 스텁으로 SayHello(HelloRequest(name)) 호출
  4. 백엔드가 HelloReply(message) 반환
  5. 게이트웨이가 {"message": ..., "elapsed_ms": ...} 로 응답

4. 코드 핵심 포인트

채널/스텁 재사용 (grpc_client.py)

channel = grpc.insecure_channel(target)        # 앱 수명 동안 1회 생성
stub = helloworld_pb2_grpc.GreeterStub(channel)

def say_hello(name: str) -> str:
    req = helloworld_pb2.HelloRequest(name=name)
    return stub.SayHello(req, timeout=5.0).message

입력 검증 (schemas.py)

class HelloRequest(BaseModel):
    name: str = Field(..., min_length=1)   # 빈 name 은 422 로 거부

5. 실무 적용 시 고려사항

이중 검증: 게이트웨이는 Pydantic 으로 1차 검증하지만, 백엔드 역시 자체 검증을 합니다. 게이트웨이를 우회하는 다른 클라이언트가 있을 수 있으므로 백엔드 검증은 신뢰의 최종 경계입니다. 본 샘플은 백엔드의 INVALID_ARGUMENT 도 400 으로 매핑해 일관된 의미를 유지합니다.
  • 채널 재사용: 채널 생성은 비쌉니다. 요청마다 만들지 말고 앱 수명 동안 재사용하세요(본 샘플은 lifespan 에서 1회 생성).
  • 타임아웃: 모든 gRPC 호출에 데드라인을 두세요. 백엔드가 응답하지 않을 때 게이트웨이 워커가 무한정 묶이는 것을 막습니다(본 샘플 timeout=5.0).
  • 스키마 분리: proto 메시지를 그대로 노출하지 말고 REST 스키마를 따로 두세요. 내부 proto 변경이 외부 API 계약으로 새지 않습니다.
  • 에러 매핑 일관성: gRPC 상태코드↔HTTP 코드 매핑 표를 한 곳에 모아 모든 엔드포인트가 같은 규칙을 쓰게 하세요.
  • 관측성: 응답 지연을 메트릭/로그로 남기세요. 본 샘플은 elapsed_ms 를 응답에 포함합니다.

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제, 포트 50052)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run uvicorn app.main:app --reload

# 통합 테스트 (결정론적 Greeter 서버를 직접 띄워 검증)
uv run pytest

통합 테스트는 /health 200, 정상 SayHello 성공 (Hello, World!), 빈 name → 422, 백엔드 INVALID_ARGUMENT → 400 을 결정론적으로 검증합니다.
