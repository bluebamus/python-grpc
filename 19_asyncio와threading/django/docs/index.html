19_asyncio와threading — Django threading 작업 큐 Django

queue.Queue + 데몬 스레드 producer/consumer 를 웹 서비스 작업 큐로 실무화하는 가이드

1. 개요 — asyncio vs threading, 언제 무엇을

이 예제는 동시성 데모 server_asyncio.py(asyncio.Queue)와 server_threading.py(queue.Queue + threading)를 각각 웹 서비스의 producer/consumer 작업 큐로 옮긴 것입니다. 본 Django 샘플은 threading 모델을 담당합니다.

구분threading (이 샘플)asyncio (FastAPI 샘플)
실행 단위여러 OS 스레드단일 스레드 + 이벤트 루프 코루틴
전환 시점OS 스케줄러가 선점적으로await 지점에서만(협력적)
큐queue.Queue (차단형 get)asyncio.Queue (put/get이 await)
공유 상태 보호복합 연산은 threading.Lock 필요락 불필요(단일 스레드)
강점블로킹 라이브러리와 호환, 단순한 모델대량 I/O 동시성, 적은 메모리

Django의 기본 WSGI 스택은 동기/블로킹입니다. 무거운 작업을 요청 안에서 직접 처리하면 워커가 묶이므로, 별도 consumer 스레드에 위임하고 요청은 즉시 task_id만 돌려주는 패턴이 자연스럽습니다.

요청은 WSGI 워커 스레드에서, 작업 처리는 별도 consumer 데몬 스레드에서 진행됩니다. gateway/worker.py가 큐·저장소·스레드를 캡슐화하고, gateway/apps.py의 ready()가 start_worker()로 consumer를 1회 기동합니다(중복 기동 방지 가드 내장).

3. 작업 흐름 (producer → queue → consumer)

  1. 클라이언트가 POST /tasks {"payload":"hello"} 호출
  2. 뷰(producer)가 worker.submit()으로 작업을 큐에 넣고 {"task_id":1,"queued":true}를 202로 즉시 반환
  3. 데몬 consumer 스레드가 차단형 queue.get()으로 작업을 꺼냄 (큐가 비면 항목이 올 때까지 대기, busy-wait 없음)
  4. _process()가 작업을 처리(블로킹). 락 밖에서 처리해 다른 스레드를 막지 않음
  5. 상태가 queued → processing → done으로 바뀌고 결과가 저장됨(락 보호)
  6. 클라이언트가 GET /tasks/1로 결과를, GET /stats로 통계를 조회

4. 코드 핵심 포인트

queue.Queue + 차단형 get + Lock (worker.py)

# producer: thread-safe 큐에 넣는다(락 불필요 — Queue가 내부에서 처리)
def submit(payload):
    with _lock:                 # 단, 작업 저장소(dict)/카운터는 직접 락으로 보호
        task_id = next(_ids)
        _tasks[task_id] = {"status": "queued", ...}
    _queue.put(task_id)
    return task_id

# consumer: 차단형 get — 큐가 빌 때까지 대기(busy-wait 없음)
def _consume():
    while True:
        task_id = _queue.get()
        with _lock: _tasks[task_id]["status"] = "processing"
        result = _process(payload)        # 락 밖에서 블로킹 처리
        with _lock:
            _tasks[task_id]["result"] = result
            _tasks[task_id]["status"] = "done"
        _queue.task_done()

# 중복 기동 방지 가드: ready()가 여러 번 불려도 스레드는 하나만
def start_worker():
    with _start_lock:
        if _started: return
        threading.Thread(target=_consume, daemon=True).start()
asyncio와의 대비: asyncio 샘플은 단일 스레드라 작업 저장소 접근에 락이 필요 없지만, threading 샘플은 여러 스레드가 같은 dict/카운터를 건드리므로 읽고-쓰는 복합 연산을 Lock으로 보호해야 합니다. 또한 asyncio가 블로킹을 asyncio.to_thread로 옮겨야 했던 것과 달리, threading 모델에서는 블로킹이 해당 스레드만 멈출 뿐 다른 스레드는 OS 스케줄러가 계속 돌립니다.

5. 실무 적용 시 고려사항

  • GIL: CPython은 한 번에 한 스레드만 파이썬 바이트코드를 실행합니다. 그래서 스레드는 I/O 바운드(대기 중 GIL 해제)에는 효과적이지만, CPU 바운드는 스레드를 늘려도 병렬 가속이 거의 없습니다. CPU 바운드는 multiprocessing/ProcessPoolExecutor가 정답입니다.
  • I/O vs CPU 바운드: 외부 API 호출·DB 등 I/O 바운드 작업을 백그라운드 스레드로 빼면 요청 워커를 묶지 않습니다. CPU 바운드는 멀티프로세스로.
  • 백프레셔(backpressure): queue.Queue(maxsize=N)으로 상한을 두면 큐가 가득 찰 때 put이 차단되어 producer를 늦춥니다. 무제한 큐는 폭주 시 메모리를 잠식합니다.
  • 그레이스풀 셧다운: 데몬 스레드는 프로세스 종료 시 즉시 정리되지만, 진행 중 작업이 잘릴 수 있습니다. 안전하게 끝내려면 sentinel을 큐에 넣어 루프를 빠져나오게 하고(데모 server_threading.py 참고) join()으로 대기하는 셧다운 훅을 둡니다.
  • 인메모리 큐 + 멀티프로세스 워커의 한계: 큐와 결과가 프로세스 메모리에만 있습니다. Gunicorn/uWSGI를 여러 워커 프로세스로 띄우면 워커마다 큐가 따로 생겨, A 워커에 넣은 작업을 B 워커가 못 봅니다(GET /tasks/{id}가 다른 워커로 라우팅되면 404). 재시작하면 큐가 사라지고 영속성/재시도도 없습니다.
  • 실무 권장: 멀티프로세스/멀티호스트 확장이나 작업 유실 방지가 필요하면 Celery + Redis/RabbitMQ 같은 외부 브로커 기반 큐를 씁니다. Django 생태계에서는 Celery가 사실상 표준입니다. 본 샘플은 단일 프로세스 학습용입니다.

6. 실행 · 테스트

# 의존성 설치
uv sync

# 서버 기동 (consumer 스레드는 앱 로드 시 자동 기동)
uv run python manage.py runserver

# 작업 투입 / 조회
curl -X POST localhost:8000/tasks -H "content-type: application/json" -d '{"payload":"hello"}'
curl localhost:8000/tasks/1
curl localhost:8000/stats

# 통합 테스트 (순수 HTTP, gRPC 불필요)
uv run pytest

통합 테스트는 작업 투입 후 consumer 스레드가 done으로 처리하는지, 여러 작업 투입 시 /stats의 처리 카운트가 증가하는지를 결정론적으로 검증합니다.
