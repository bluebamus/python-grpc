19_asyncio와threading — FastAPI asyncio 작업 큐 FastAPI

asyncio.Queue 기반 producer/consumer 를 웹 서비스 작업 큐로 실무화하는 가이드

1. 개요 — asyncio vs threading, 언제 무엇을

이 예제는 동시성 데모 server_asyncio.py(asyncio.Queue)와 server_threading.py(queue.Queue + threading)를 각각 웹 서비스의 producer/consumer 작업 큐로 옮긴 것입니다. 본 FastAPI 샘플은 asyncio 모델을 담당합니다.

판단 기준: I/O 바운드 + 고동시성이고 라이브러리가 async를 지원하면 asyncio가 유리합니다. 반대로 동기/블로킹 라이브러리만 있거나 CPU 바운드라면 threading(또는 멀티프로세스)이 현실적입니다.

요청 처리와 consumer 코루틴은 같은 이벤트 루프 위에서 협력적으로 동시에 돕니다. app/worker.py가 큐·저장소·consumer를 캡슐화하고, app/main.py의 lifespan이 기동/셧다운을 관리합니다.

3. 작업 흐름 (producer → queue → consumer)

  1. 클라이언트가 POST /tasks {"payload":"hello"} 호출
  2. 핸들러(producer)가 await queue.submit()으로 작업을 큐에 넣고 {"task_id":1,"queued":true}를 202로 즉시 반환
  3. 백그라운드 consumer 코루틴이 await queue.get()으로 작업을 꺼냄 (대기 중에는 제어를 루프에 넘겨 다른 요청이 처리됨)
  4. 블로킹 처리 함수는 asyncio.to_thread()로 별도 스레드에서 실행
  5. 상태가 queued → processing → done으로 바뀌고 결과가 저장됨
  6. 클라이언트가 GET /tasks/1로 결과를, GET /stats로 통계를 조회

4. 코드 핵심 포인트

asyncio.Queue + await (worker.py)

# producer: await put — 큐가 가득 찼을 때만 대기(백프레셔)
async def submit(self, payload):
    task_id = next(self._ids)
    self._tasks[task_id] = {"status": "queued", ...}
    await self._queue.put(task_id)
    return task_id

# consumer: await get — 항목이 올 때까지 비동기 대기(busy-wait 없음)
async def _consume(self):
    while True:
        task_id = await self._queue.get()
        record["status"] = "processing"
        result = await asyncio.to_thread(_blocking_process, ...)  # 블로킹은 to_thread!
        record["status"] = "done"
        self._queue.task_done()
블로킹 호출은 반드시 asyncio.to_thread()로 감싼다. 데모 server_asyncio.py가 input()을 to_thread로 감싼 이유와 같습니다. time.sleep()·동기 DB 드라이버·requests 같은 동기 호출을 코루틴에서 그냥 부르면, 그 시간 동안 이벤트 루프 전체가 멈춰 다른 요청과 consumer가 모두 정지합니다. to_thread는 호출을 별도 스레드로 던지고 await로 완료를 기다려 루프를 살려 둡니다.
패턴asynciothreading
큐 넣기await queue.put(x)queue.put(x)
큐 꺼내기await queue.get()queue.get() (차단)
블로킹 작업await asyncio.to_thread(fn)스레드가 직접 실행

5. 실무 적용 시 고려사항

  • GIL: CPython은 한 번에 한 스레드만 파이썬 바이트코드를 실행합니다. asyncio는 애초에 단일 스레드라 GIL 경합이 없지만, CPU 바운드 작업은 to_thread로 옮겨도 GIL 때문에 병렬 가속이 안 됩니다. CPU 바운드는 ProcessPoolExecutor/멀티프로세스가 정답입니다.
  • I/O vs CPU 바운드: 네트워크/디스크 대기가 많은 I/O 바운드는 asyncio가 적은 자원으로 높은 동시성을 냅니다. CPU 바운드는 멀티프로세스로.
  • 백프레셔(backpressure): asyncio.Queue(maxsize=N)으로 상한을 두면 큐가 가득 찰 때 await put이 대기하여 producer 속도를 자동으로 늦춥니다(설정 WORKER_QUEUE_MAXSIZE). 무제한 큐는 폭주 시 메모리를 잠식합니다.
  • 그레이스풀 셧다운: 본 샘플은 lifespan 종료 시 queue.join()으로 남은 작업을 모두 처리한 뒤 consumer를 취소합니다. 그냥 종료하면 큐에 남은 작업이 유실됩니다.
  • 인메모리 큐의 한계: 큐와 결과가 프로세스 메모리에만 있습니다. Uvicorn/Gunicorn을 --workers N으로 띄우면 워커마다 큐가 따로 생겨, A 워커에 넣은 작업을 B 워커가 못 봅니다. 재시작하면 큐가 사라지고 재시도/영속성도 없습니다.
  • 실무 권장: 멀티프로세스/멀티호스트로 확장하거나 작업을 잃으면 안 된다면 Celery + Redis/RabbitMQ, Dramatiq, arq 같은 외부 브로커 기반 큐를 씁니다. 본 샘플은 단일 프로세스 데모/학습용입니다.

6. 실행 · 테스트

# 의존성 설치
uv sync

# 서버 기동
uv run uvicorn app.main:app --reload

# 작업 투입 / 조회
curl -X POST localhost:8000/tasks -H "content-type: application/json" -d '{"payload":"hello"}'
curl localhost:8000/tasks/1
curl localhost:8000/stats

# 통합 테스트 (순수 HTTP, gRPC 불필요)
uv run pytest

통합 테스트는 작업 투입 후 consumer가 done으로 처리하는지, 여러 작업 투입 시 /stats의 처리 카운트가 증가하는지, 그리고 동시에 투입한 작업이 이벤트 루프를 막지 않고 전부 처리되는지 (test_concurrent_submissions_do_not_block_event_loop)를 검증합니다.
