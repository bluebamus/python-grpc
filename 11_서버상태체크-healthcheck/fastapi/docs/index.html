11_서버상태체크 — FastAPI HTTP→gRPC 헬스체크 게이트웨이 FastAPI

표준 gRPC 헬스체크(grpc.health.v1)를 REST 로 노출해 운영·모니터링에 연결하는 가이드

1. 개요 — 실무에서 어디에 쓰나

마이크로서비스 환경에서 각 서비스는 자신의 서빙 상태를 표준 헬스체크 프로토콜 grpc.health.v1.health/Check 로 노출합니다. 쿠버네티스의 liveness/readiness probe, 로드밸런서의 헬스체크, 배포 파이프라인의 준비 확인 등이 이 신호를 사용합니다.

하지만 모든 인프라가 gRPC 를 직접 호출할 수 있는 것은 아닙니다. HTTP→gRPC 헬스체크 게이트웨이는 외부에 단순한 REST 엔드포인트(GET /health/grpc) 를 제공하고, 내부적으로 gRPC Check 를 호출해 ServingStatus 를 HTTP 상태코드로 번역합니다. SERVING 이면 200, 그 외에는 503 으로 매핑하면 표준 HTTP 헬스체크를 기대하는 어떤 도구와도 곧바로 연동됩니다.

백엔드가 ServingStatus 를 반환하면 게이트웨이가 이를 HTTP 상태코드로 변환합니다. SERVING → 200, NOT_SERVING / SERVICE_UNKNOWN / UNKNOWN → 503.

3. 호출 흐름 (단계별)

  1. 모니터링 도구가 GET /health/grpc?service=api 호출
  2. 게이트웨이가 재사용 중인 gRPC 스텁으로 Check(service="api") 호출
  3. 백엔드 헬스 서버가 해당 서비스의 ServingStatus 를 응답
  4. 게이트웨이가 상태를 HTTP 코드로 매핑 (SERVING→200, 그 외→503)
  5. Check 자체가 gRPC 에러(예: NOT_FOUND, UNAVAILABLE)로 끝나면 에러 매핑 테이블로 변환

게이트웨이 자체의 살아있음은 별도로 GET /health 가 항상 200 으로 알려줍니다(백엔드 상태와 무관).

4. 코드 핵심 포인트

5. 실무 적용 시 고려사항

liveness 와 readiness 를 구분하세요. liveness 는 "프로세스가 살아있나"(죽었으면 재시작), readiness 는 "트래픽을 받을 준비가 됐나"(아니면 LB 에서 제외) 입니다. 같은 200/503 매핑이라도 두 probe 가 가리키는 서비스명/의미를 분리해 두는 것이 안전합니다.
  • 타임아웃은 짧게: 헬스체크는 빨라야 합니다. Check 데드라인을 수 초 이하로 두어 느린 백엔드가 게이트웨이를 막지 않게 하세요(본 샘플 기본 2초).
  • Watch 스트리밍: 폴링 대신 Watch 로 상태 변화를 구독하면 상태 전이를 즉시 받을 수 있습니다. SSE/WebSocket 으로 프런트에 중계하기 좋습니다.
  • 게이트웨이 자체 헬스 분리: /health 는 백엔드와 무관하게 200 이어야 합니다. 그래야 "게이트웨이는 살아있지만 백엔드가 죽음"을 구분할 수 있습니다.
  • 503 의 캐시 금지: 헬스 응답에 캐시가 끼면 장애 복구가 늦게 반영됩니다. 프록시/CDN 에서 헬스 경로는 캐시하지 않도록 하세요.
  • 채널 재사용: 채널 생성은 비쌉니다. 요청마다 만들지 말고 앱 수명 동안 재사용하세요(본 샘플은 lifespan 에서 1회 생성).
  • 인증/노출 범위: 헬스 엔드포인트가 내부 토폴로지를 흘리지 않게, 외부 노출 시 서비스명 목록·상세 사유는 최소화하세요.

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 헬스체크 서버 (상위 폴더 예제, 포트 50061)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run uvicorn app.main:app --reload

# 통합 테스트 (헬스 서버를 직접 띄워 상태/매핑 검증)
uv run pytest

통합 테스트는 서비스명→상태 매핑을 지정한 결정론적 헬스 서버로, SERVING→200, NOT_SERVING→503, 알 수 없는 서비스→503 매핑이 실제로 일어나는지 결정론적으로 검증합니다.
