13_타임아웃설정과통신연결유지기법 — Django HTTP→gRPC 게이트웨이 Django

per-call 데드라인과 keepalive 로 "느린 백엔드"와 "죽은 연결"을 실무에서 다루는 가이드

1. 개요 — 실무에서 어디에 쓰나

Django 로 운영 중인 웹/관리자 서비스가 내부 gRPC 마이크로서비스를 호출할 때, 백엔드가 가끔 느려지면(GC, 콜드 캐시, 일시 과부하) 요청 스레드가 무한정 묶여 장애가 전파됩니다. 각 호출에 per-call deadline(timeout) 을 걸어 빠르게 실패시키면 이를 막을 수 있고, gRPC 의 DEADLINE_EXCEEDED 를 HTTP 504 로 변환해 클라이언트에 일관된 의미로 알립니다.

게이트웨이는 채널을 오래 재사용하므로, 유휴 구간에 연결이 조용히 끊기는 것을 막기 위해 keepalive 옵션으로 주기적 PING 을 보내 연결을 살립니다.

채널/스텁은 get_client() 로 프로세스 단위 재사용됩니다(keepalive 로 장수명 유지). 요청마다 데드라인을 적용하며, 백엔드가 데드라인을 넘기면 뷰가 504 로 변환합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /echo {"message":"Hello","deadline_ms":1000} 호출
  2. Django 뷰가 JSON 파싱·검증 (빈 문자열 → 422)
  3. get_client() 로 재사용 중인 gRPC 스텁의 Echo(request, timeout=...) 호출
  4. 백엔드가 데드라인 안에 응답하면 결과를 그대로 반환
  5. 데드라인 초과 시 gRPC 가 DEADLINE_EXCEEDED → 뷰가 504 로 매핑

4. 코드 핵심 포인트

설정 분리 (config/settings.py)

GRPC_TARGET = os.environ.get("GRPC_TARGET", "localhost:50063")
GRPC_DEFAULT_DEADLINE_MS = int(os.environ.get("GRPC_DEFAULT_DEADLINE_MS", "1000"))
GRPC_KEEPALIVE_TIME_MS = int(os.environ.get("GRPC_KEEPALIVE_TIME_MS", "10000"))
# ... keepalive_timeout_ms / permit_without_calls / max_pings_without_data

keepalive + 채널 재사용 (gateway/grpc_client.py)

options = [
    ("grpc.keepalive_time_ms", settings.GRPC_KEEPALIVE_TIME_MS),
    ("grpc.keepalive_timeout_ms", settings.GRPC_KEEPALIVE_TIMEOUT_MS),
    ("grpc.keepalive_permit_without_calls", 1),
    ("grpc.http2.max_pings_without_data", 0),
]
channel = grpc.insecure_channel(target, options=options)

def get_client():           # 채널 1회 생성 후 프로세스 단위 재사용
    global _client
    if _client is None:
        _client = GrpcClient()
    return _client

per-call deadline (gateway/grpc_client.py)

timeout_s = deadline_ms / 1000.0   # gRPC timeout 은 초 단위 float
response = stub.Echo(EchoRequest(message=message), timeout=timeout_s)

5. 실무 적용 시 고려사항

WSGI 동기 모델: Django 동기 뷰에서 gRPC 동기 호출은 요청 스레드를 블로킹합니다. 데드라인이 너무 길면 느린 백엔드가 워커 스레드를 모두 묶어버립니다. 데드라인을 짧게·합리적으로 두는 것이 스레드 고갈을 막는 1차 방어선입니다.
  • 데드라인 전파: A→B→C 호출 체인에서 남은 데드라인이 전파되어 이미 늦은 요청에 추가 작업을 쌓지 않습니다. 각 단계 데드라인을 일관되게 설계하세요.
  • 채널과 fork: gunicorn prefork 시 채널은 fork 이후(워커 안)에서 만들어야 합니다. 본 샘플의 지연 생성(get_client)이 이를 만족합니다.
  • keepalive 과도 설정 주의: PING 주기가 서버의 min_time_between_pings_ms 보다 짧으면 too_many_pings 로 연결이 끊깁니다. 서버 설정과 맞추세요.
  • 유휴 연결과 LB/방화벽: 중간 장비 idle timeout 보다 짧은 주기로 keepalive 를 보내야 연결이 조용히 끊기는 것을 막습니다.
  • 서버 측 취소 처리: 데드라인 초과 시 서버는 context.is_active() 로 취소를 감지해 불필요한 작업을 중단해야 자원이 낭비되지 않습니다.

6. 실행 · 테스트

uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제, 포트 50063 으로)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run python manage.py runserver

# 통합 테스트
uv run pytest

통합 테스트는 서버가 일부러 2초 sleep 하도록 만들고 200ms 데드라인으로 호출해, DEADLINE_EXCEEDED 가 504 로 매핑되는지 결정론적으로 검증합니다.
