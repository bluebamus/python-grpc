13_타임아웃설정과통신연결유지기법 — FastAPI HTTP→gRPC 게이트웨이 FastAPI

per-call 데드라인과 keepalive 로 "느린 백엔드"와 "죽은 연결"을 실무에서 다루는 가이드

1. 개요 — 실무에서 어디에 쓰나

마이크로서비스 환경에서 백엔드는 가끔 느려집니다(GC, 콜드 캐시, 일시적 과부하). 게이트웨이가 응답을 무한정 기다리면 워커가 묶이고 장애가 전파됩니다. 그래서 per-call deadline(timeout) 을 걸어 "이 시간 안에 못 끝내면 포기"하고 빠르게 실패시키는 것이 중요합니다. gRPC 는 이를 DEADLINE_EXCEEDED 로 알려주고, 게이트웨이는 이를 HTTP 504 로 변환합니다.

또한 게이트웨이는 채널을 오래 열어두고 재사용합니다. 트래픽이 없는 유휴 구간에 방화벽/로드밸런서가 조용히 연결을 끊으면, 다음 호출에서 갑자기 실패합니다. keepalive 는 주기적으로 HTTP/2 PING 을 보내 연결을 살리고, 죽은 연결을 빨리 감지해 재연결하게 합니다.

요청마다 게이트웨이가 데드라인(deadline_ms 또는 기본값)을 적용해 호출합니다. 백엔드가 데드라인을 넘기면 채널이 호출을 끊고 DEADLINE_EXCEEDED 를 던지며, 게이트웨이는 504 로 변환해 클라이언트에 응답합니다.

3. 호출 흐름 (단계별)

  1. 클라이언트가 POST /echo {"message":"Hello","deadline_ms":1000} 호출
  2. FastAPI 가 Pydantic 으로 입력 검증 (빈 문자열 → 422)
  3. 게이트웨이가 재사용 중인 gRPC 스텁으로 Echo(request, timeout=deadline_ms/1000) 호출
  4. 백엔드가 데드라인 안에 응답하면 결과를 그대로 반환
  5. 데드라인 초과 시 gRPC 가 DEADLINE_EXCEEDED → 게이트웨이가 504 로 매핑

4. 코드 핵심 포인트

keepalive 옵션 주입 (grpc_client.py)

options = [
    ("grpc.keepalive_time_ms", 10000),            # 10s 마다 PING
    ("grpc.keepalive_timeout_ms", 5000),          # PING 응답 5s 대기
    ("grpc.keepalive_permit_without_calls", 1),   # 유휴에도 PING 허용
    ("grpc.http2.max_pings_without_data", 0),     # 데이터 없이 PING 무제한
]
channel = grpc.insecure_channel(target, options=options)

per-call deadline 적용 (grpc_client.py)

# gRPC 의 timeout 은 '초' 단위 float. ms 를 초로 환산한다.
timeout_s = deadline_ms / 1000.0
response = stub.Echo(EchoRequest(message=message), timeout=timeout_s)

5. 실무 적용 시 고려사항

데드라인은 호출 체인 전체로 전파(propagation)됩니다. A→B→C 로 호출이 이어질 때, 남은 데드라인이 자동으로 전달되어 이미 늦은 요청에 추가 작업을 쌓지 않습니다. 그래서 각 단계의 데드라인을 일관되게 설계하는 것이 중요합니다.
  • 데드라인 vs 타임아웃: gRPC 는 "절대 시각" 개념의 데드라인을 씁니다. 본 샘플은 호출 시점 기준 상대 시간(timeout)으로 지정합니다.
  • 너무 짧은 데드라인: 정상 처리 시간보다 짧으면 항상 504 가 됩니다. p99 지연을 측정해 여유를 둔 값으로 설정하세요.
  • keepalive 과도 설정 주의: PING 주기가 너무 짧으면 서버가 too_many_pings 로 연결을 끊을 수 있습니다. 서버의 grpc.http2.min_time_between_pings_ms 와 맞춰야 합니다.
  • 유휴 연결과 LB/방화벽: 중간 장비의 idle timeout 보다 짧은 주기로 keepalive 를 보내야 연결이 조용히 끊기는 것을 막습니다.
  • 서버 측 취소 처리: 데드라인 초과 시 클라이언트는 포기하지만, 서버는 context.is_active() 등으로 취소를 감지해 불필요한 작업을 중단해야 자원이 낭비되지 않습니다.
  • 채널 재사용: 채널 생성은 비쌉니다. 앱 수명 동안 재사용하세요(본 샘플은 lifespan 에서 1회 생성, keepalive 로 장수명 유지).

6. 실행 · 테스트

# 의존성 설치
uv sync

# 백엔드 gRPC 서버 (상위 폴더 예제, 포트 50063 으로)
cd .. && uv run python server.py

# 게이트웨이 기동
uv run uvicorn app.main:app --reload

# 통합 테스트 (gRPC 서버를 직접 띄워 deadline/매핑 검증)
uv run pytest

통합 테스트는 서버가 일부러 2초 sleep 하도록 만들고 200ms 데드라인으로 호출해, DEADLINE_EXCEEDED 가 504 로 매핑되는지 결정론적으로 검증합니다.
